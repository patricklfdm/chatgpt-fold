# 0.2：能否保留折叠条，由原站卸载助手正文？

**判断：找到了适合作为折叠条宿主的结构，也找到了创建助手内容的组件；在这条会话渲染链里，没有找到供扩展按消息调用的卸载／重建入口。** 维持 0.1.7 的展示折叠，不将以下内部业务状态接入生产按钮。

## 真实页对照给出了什么依据

[折叠与窗口实验](FOLD_WINDOW_EXPERIMENT.md) 的一次真实页 `strict` 对照取得了三个阶段的全部样本。同一锚点的正文在折叠时无布局框，旁路样式时出现布局框，恢复后又消失。原生轮次外壳数、助手正文标记数、原生轮次元素数在三个阶段相同。B 阶段的扩展控制器仍运行。

因此，在这次原地切换中**没有观察到窗口扩大或收缩**。相同计数不证明每个节点的身份相同，也不能确定是原站的范围保留规则所致。它足以作为“只改变 CSS”的对照，不能回答标签页进程内存或持续生成时的峰值问题；无需为了检验同一处 CSS 再运行探针。以下调查针对一个不同的问题：谁能让可见答案的正文真正退出组件树？

## 谁拥有正文

1. 会话页面把轮次交给列表和行组件。列表控制整行是否进入渲染集合；行组件把原轮次交给轮次 renderer。详见[第一轮源码调查](NATIVE_VIRTUALIZER_FINDINGS.md)。
2. 在本次追踪的普通助手消息分支中，轮次 renderer 按项目类型分别处理用户消息与助手消息。助手分支创建带搜索单元键、消息身份的外层元素，在它里面创建答案组件和兄弟项。**可保留的宿主是助手自己的外壳，而不是同时包住用户提问的整轮。** 特殊可视化内容甚至可能把一轮拆成多个列表 entry，不能普遍假设轮次与回答一一对应。
3. 答案组件内部创建 Markdown，并组合文件资源、浏览器交接链接、声明等按条件出现的内容。Markdown 根标记能帮助测量，但删掉或省略 Markdown 不等于省略完整助手内容。轮次级工具、资源和操作可能又在这一单元外；实验不能顺手移除它们。
4. 理想的输入应该由网页组件拥有：给指定、已完成的助手消息一个折叠标志；保留其身份外壳，条件化创建该消息的正文。展开时由同一 renderer 从对话数据重建正文。这描述了**所需能力**，并非现有 API。

### 哪些相似入口不能接

| 发现 | 实际作用 | 对逐回答折叠的结论 |
| --- | --- | --- |
| 助手搜索单元的 `hidden` / `inert` | 来自特定内容的准备状态；外壳仍收到子组件 | 知道属性名不足以让 React 卸载子树 |
| Markdown 的 `renderRoot` | 接受调用方提供的 token 渲染回调。追踪到的助手调用没有提供由扩展控制的回调 | 自定义 Markdown 内容也无法移除外层组件和资源兄弟；不是针对现存消息的命令 |
| `pendingAlternate` | 部分最新轮次切换回答版本时，非用户项会被替换成加载提示或空项 | 确有条件移除，但作用于版本切换及一组内容，不适用于任意已完成的历史回答 |
| `hideInitialUserMessage` | 只在相应模式下过滤第一轮的用户项 | 按角色过滤的先例不提供助手消息的逐条开关 |

这些结论来自实际页面先前列出的静态资源，未执行下载的 JS，也未推定用户本次实例走了 Work、普通会话、可视化或备选回复中的某一特殊分支。

## 实测：如果页面只移除正文，现有折叠条会怎样？

用 [assistant-body-host.cjs](../tests/assistant-body-host.cjs) 搭建两条已完成问答的合成页面。加载 0.1.7 的实际样式和内容脚本，隔离世界由 Chromium 提供，Chrome 扩展 API 用测试替身。页面自己移除、重建节点；没有加载 ChatGPT renderer 或模拟一个可以从扩展调用的原站开关。

| 页面保留的宿主 | 正文缺失期间 | 页面显式重建后 |
| --- | --- | --- |
| 明确标识为助手的搜索单元，保留强消息身份 | 原折叠条仍可点；原首行摘要不再显示。点击改变展开意图，正文仍不存在 | 原折叠条保留，新的正文可见 |
| 整个助手单元一起移除，仅留外层问答轮次 | 原按钮和助手单元一起断开，不能在原处点击 | 扩展重新发现助手单元并创建新按钮 |
| 留下只有消息 ID、无明确作者角色的载体 | 载体仍连接，但失去正文后不再满足助手识别条件，原折叠条被清理 | 恢复正文后重新识别，创建新按钮 |

在后两组中，先手动展开目标以检验重挂载后的选择。三组中问题和相邻回答均保持；页面显式重建后，目标保持展开，新页面按钮能调用新安装的监听器。保留助手外壳因此**只解决按钮宿主的一部分问题**：可靠的角色与身份、有界的一行摘要、网页拥有的重新挂载入口是三个不同条件。不能只留下任意空 div 或一个消息 ID。

复现命令：`npm run test:body-host`（可用 `CHROME_PATH` 指定 Chromium）。在 Chromium 153 / Node.js 24 下 **3/3 个场景通过**。这是折叠扩展对三种 DOM 形状的兼容性验证；测试保留旧节点引用以核对身份，不能用于推断 GC、内存净收益、真实 React 局部状态或 ChatGPT 的代码／引用组件已通过验收。

## 进入真实页干预的门槛

只有取得**网页自身可逆、可定位单条已完成回答**的控制输入，才值得做一次真实页干预。应同时观察：屏幕内轮次与用户问题保持，轻量折叠条仍可点，目标正文实际断开，邻居不变；点击后由网页重新创建正文，代码、引用、附件等交互分别验收。重新创建原生组件并不保证其临时局部状态自动恢复，见 [React 状态与渲染树](https://react.dev/learn/preserving-and-resetting-state)。

目前没有满足条件的调用点。直接移除网页管理的 DOM、缓存 HTML 后插回、模拟版本切换或强制滚出屏幕，都不能验证所需入口。手工移除节点还可能与后续 React 更新冲突，见 [React 的 DOM 操作说明](https://react.dev/learn/manipulating-the-dom-with-refs)。

若目标改为量化现有版本对崩溃风险的影响，应独立测量长会话持续追加时的进程内存与 JS 内存走势，记录峰值和回到同一状态后的读数；无需把这项测量和私有 renderer 接入捆绑。任务管理器两种指标的含义见 [Chrome 内存排查文档](https://developer.chrome.com/docs/devtools/memory-problems)。

# 架构说明

## 目标与范围

ChatGPT Fold 0.1.2 实现逐条回答折叠。目标是在保留随时展开能力的前提下，限制同时参与布局和绘制的回答数量。

使用者将内存占用置于首位，因此实现需要避免引入第二份完整聊天记录、HTML 字符串快照、离屏 DOM 树或大量持久缓存。本版选择较保守的 DOM 可见性控制；真实收益由测量确认。

本版不实现视口虚拟化，不修改 ChatGPT 的服务端对话，不接管站点的 React 渲染，也不读取内部 store、Fiber 或私有接口。

## 技术组成

| 文件 | 职责 |
| --- | --- |
| `manifest.json` | Manifest V3、站点匹配、内容脚本顺序、弹窗和 storage 权限 |
| `src/shared.js` | 默认配置、输入归一化，以及可独立验证的通用逻辑 |
| `src/adapter.js` | 查找助手回答、选择可折叠区域、检查页面保护条件 |
| `src/content.js` | 初始化与增量发现、折叠 / 展开状态、事件处理、弹窗通信、清理 |
| `src/content.css` | 单行摘要、按钮、主题适配和隐藏规则 |
| `src/popup.*` | 偏好编辑、当前页状态、临时恢复和批量操作 |

代码使用原生 JavaScript、CSS 和 Chrome 扩展 API。运行时不需要打包器、框架或远程依赖。

## 折叠机制

### 页面结构与识别边界

适配器保留旧版 `[data-message-author-role="assistant"]`、`[data-turn="assistant"]`，并在 0.1.2 中增加新版消息结构。选择规则按语义与范围确定，不依赖消息奇偶、普通段落或 `.markdown` 类名。

| 依据 | 折叠范围与限制 |
| --- | --- |
| `data-message-author-role` / `data-message-role` 为 `assistant` | 明确助手容器；检查冲突与嵌套后使用有效的外层容器 |
| `data-chatgpt-search-unit-key` / `data-content-search-unit-key` 以 `:assistant` 结尾 | 明确助手单元；两层同时存在时只登记一条回答 |
| `data-turn="assistant"` | 保留旧版补充规则；内部有明确角色容器时优先识别内部 |
| 消息标识容器带有或包含 `data-markdown-text-style="assistant-message"` 正文 | 仅在自身与嵌套标识一致且没有内部角色 / 单元标记时，作为补充根；重复的同一 ID 可归一，冲突或多个不同 ID 不用于推断整个容器 |
| 带助手正文标记的内容本身 | 只有处于已知消息标识、角色或轮次上下文中，且没有可用的外层候选时，才作为较小的补充范围；缺少可靠分组依据时，不把同一容器中的多个裸正文片段分拆成多条回答 |

用户角色、`:user` 单元和 `data-user-message-bubble="true"` 均参与排除。候选自身、祖先或内部出现相关冲突时，保留原内容。单纯拥有消息 ID、`data-turn-key` 或 `data-talvt-turn-state` 不能证明它是助手回答；整个现代轮次可能同时包含提问与回答，因此这些轮次属性不单独产生折叠根。

有可靠单元或身份一致的消息容器时，多段正文共用一个控制栏；无法确定该范围时保留内容显示。选择标识与搜索标识同时存在时也必须一致，避免以其中一个标识掩盖另一个冲突。

本次实际结构报告确认选中回答在顶层聊天文档中，并包含搜索消息容器与 turn 状态属性；探针并未导出新版 unit key 的原始值。新规则同时参考了作者自己的[浏览器适配假设](https://github.com/qayshp/chatgpt-playwright-backend)、[DOM 实测记录](https://github.com/JoonJ14/ai-conversation-navigator/blob/main/DOM-REFERENCE.md)和[新渲染器与隐藏工作区记录](https://github.com/aweffr/chatgpt-markdown-exporter/blob/master/docs/plans/2026-10-09-dil-renderer-probe.md)。这些资料支持页面家族的兼容方向，不构成 OpenAI 稳定接口承诺，也不替代使用者当前页面上的验收。

### 应用与恢复可见性

对支持的回答，扩展为其添加小型控制栏，并给原有的直接内容容器添加折叠样式。收起时使用 `display: none`；展开时移除扩展自己的隐藏条件。原有节点保留在原来的 DOM 关系中，站点的事件处理和组件状态仍由站点维护。

原站结构无法明确识别时，扩展应保留内容显示。不能把一个不确定的大范围容器直接隐藏，以免连输入框、用户问题或整段页面一起收起。弹窗中的未支持数量帮助定位这类适配问题。

### 活动文档与隐藏副本

SPA 可能保留仍连接到 DOM 的旧工作区。识别会排除 `hidden`、明确的 `aria-hidden="true"`、CSS `display:none` / 隐藏可见性，以及 `data-app-action-timeline-scroll` 上的 `role="presentation"` 时间线。只存在 `isConnected` 并不足以把内容算入当前活动回答。

这不是视口过滤：屏幕外的已挂载回答仍可识别；`display:contents` 容器没有自己的布局盒，也不因此被排除。检查不逐条测量回答几何位置。同一轮发现与无效记录清理共用短期缓存，重复的祖先显示状态和候选判断可以复用，整轮结束后丢弃，避免缓存可见性跨页面更新失效。

### 为什么保留原节点

原站框架可能仍持有节点和组件引用。将节点移出、替换成自行恢复的 HTML 或删除后重建，会增加后续生成、分支切换、复制按钮等功能失效的风险。

初版通过添加控件和修改可见性来降低侵入程度。它仍然需要真实页面验证；浏览器扩展对第三方应用 DOM 的修改始终受页面版本影响。

### 为什么这不等于卸载内容

`display: none` 使隐藏元素不产生正常的布局盒（见 [MDN 的 display 说明](https://developer.mozilla.org/en-US/docs/Web/CSS/display)），但不会删除 DOM 对象，也不会释放仍被站点引用的回答数据。图片解码缓存、字体、浏览器内部资源、React 状态及 JavaScript 堆的回收时机也不能由这个开关直接保证。

因此，内存分析必须分开观察：

- **渲染工作与渲染相关内存：** 折叠可能产生收益，需要测量。
- **DOM 数量：** 原内容仍存在，不应声称已删除或大幅下降；扩展控件还会增加少量节点。
- **JavaScript 堆：** 未主动卸载站点对象，不保证下降。
- **Chrome 标签页 / 进程总内存：** 受多种分配与缓存影响，可能不会立即返还给操作系统。

CSS 的 `content-visibility` 也主要是渲染优化工具；单独使用它同样不能证明站点数据或组件状态被卸载。参考 [web.dev 的说明](https://web.dev/articles/content-visibility)。

## 展开策略

偏好结构为：

```json
{
  "enabled": true,
  "keepRecent": 1,
  "maxExpanded": 1
}
```

设置键为 `cgf.settings.v1`，存入 `chrome.storage.local`。输入需要归一化：

- `keepRecent` 为 0–5 的整数。
- `maxExpanded` 为 1–5 的整数。
- 默认展开数量不得大于同时展开上限。
- 缺失或无效的值回到安全的有效配置。

默认初始化时展开最新 1 条普通回答。用户主动展开旧回答后，策略按上限收起其他普通回答。一个回答可以通过自己的控制栏再次收起。

“普通回答”指没有生成、编辑或文字选区保护的回答。保护内容暂时独立于数量上限；这样不会因执行折叠策略而打断正在交互的回答。

## 保护条件与局限

| 条件 | 期望行为 | 需要真实页面确认的内容 |
| --- | --- | --- |
| 正在生成 | 暂时保持相关回答展开 | 生成标记和停止按钮的页面结构 |
| 正在编辑 | 暂时保留编辑区域及所属回答 | 编辑器、焦点和分支选择的结构 |
| 存在文字选区 | 保留包含选区的回答 | 鼠标、键盘、多节点选区及选区解除 |
| 未支持结构 | 不折叠原内容 | 页面结构变化后的可识别边界 |

保护可能使用站点属性、控件和 DOM 变化等信号；这些都不是对外稳定接口。保护识别不等于能理解所有页面交互，因此发布前需要按[测试说明](TESTING.md)进行真实页面验收。

0.1.2 在保留原有生成信号的同时，增加 `form[data-chatgpt-composer]` 内 `aria-label="Stop"` / `"停止"` 按钮的识别。普通回答里的同名按钮不触发这条规则，隐藏工作区中的停止控件也不用于保护当前回答。`data-talvt-turn-state` 的变化会被观察，但不猜测所有非 `complete` 值都是生成中，更不根据它决定作者。

## 更新与清理

内容脚本需要处理首次加载、动态插入、生成过程以及 SPA 内的对话切换。观察回调应合并短时间内的变化，避免每生成一个 token 就重新扫描、遍历或复制整个历史。

0.1.1 的增量扫描会回查已知助手角色或助手 turn 祖先。子节点发生删除时，也检查仍连接在页面上的语义容器，而不仅扫描新增节点。这解决了“内层角色标记消失后，外层 fallback 已符合条件却没有被重新发现”的漏扫路径。扫描队列合并包含关系，日常更新不增加定时全页轮询。

0.1.2 将新增角色、unit key、消息标识和正文属性纳入增量观察。`class`、`style`、`hidden`、`aria-hidden`、`role` 变化可能让缓存工作区切换显示，因此会在相关容器中重新检查候选与记录。单纯样式变化不会被当成正文更新来设置生成保护或重新提取摘要。已隐藏的工作区释放扩展记录，恢复显示后按当前设置重新发现。

用户点击重新扫描时执行一次完整发现与无效记录清理。弹窗请求状态且登记数量为 0 时，也可以触发一次重扫，两次此类尝试至少间隔 2 秒；它由请求触发，不是后台定时器。若 `document.body` 已被替换，处理刷新状态或重扫时会释放旧树记录并重新连接观察器。

回答记录仅保留当前页面交互所需的引用与少量状态。回答被移除或页面切换时，应清理无效引用、观察关系和扩展控件，避免扩展成为新的长期内存持有者。

禁用扩展效果时应恢复原内容的可见性；扩展注入的属性和控件应有独立命名，避免覆盖原站样式和数据。

## 弹窗通信与当前页状态

内容脚本向弹窗提供识别数量、已折叠数量、展开数量、保护数量、未支持数量、版本及启用 / 扫描运行 / 暂停状态。`enabled` 只表示设置开启，`active` 表示折叠扫描器已启动。弹窗不会仅凭设置开启就把 0 条回答描述为正常识别。

内部消息约定：

```js
{ type: 'CGF_GET_STATUS' }
{ type: 'CGF_GET_DIAGNOSTICS' }
{ type: 'CGF_COMMAND', command: 'collapse-all' }
{ type: 'CGF_COMMAND', command: 'recent' }
{ type: 'CGF_COMMAND', command: 'restore' }
{ type: 'CGF_COMMAND', command: 'resume' }
{ type: 'CGF_COMMAND', command: 'rescan' }
```

`restore` 临时恢复当前页面并暂停折叠，便于原生搜索或排查；`resume` 继续按设置折叠。临时恢复不改变长期偏好。已关闭页面或没有内容脚本响应时，弹窗应提供可理解的状态，而不是假定命令成功。

`rescan` 返回普通状态结构。设置关闭或本页暂停时，它只检查当前可识别数量，不隐式启用或恢复折叠。弹窗与内容脚本版本不一致时，弹窗要求刷新 ChatGPT 页面，并停用页面操作，避免继续使用旧脚本。

`CGF_GET_DIAGNOSTICS` 返回 `{ ok: true, diagnostics: { ... } }`。0.1.2 使用 `schemaVersion: 2`，保留原有固定字段并增加 `modern` 计数对象，覆盖角色别名、两种助手单元、助手正文、搜索 / 选择消息容器、用户气泡、轮次容器和不可见候选。适配器还统计可用候选及嵌套或冲突排除；控制器附加登记数量与观察器连接状态。各类原始标记可能重叠，不能直接求和作为回答总数。

角色分布中的未知值只计入 `other`。报告不返回正文、HTML、URL、消息 ID、unit key 原值、页面标题或任意属性原值；不扫描跨文档内容，也不写入持久存储。

该报告用于区分识别器没有匹配、候选被保守排除、扫描器未登记这几种情况。没有实际页面结构证据时，不能仅凭“已启用、0 条”确认页面已经改版或认定某个漏扫路径就是用户遇到的原因。

## 权限与数据

- 仅声明 `storage` 权限。
- 内容脚本范围为 `https://chatgpt.com/*`。
- 继续只处理顶层文档，不因页面存在 iframe 就扩大注入或站点权限。
- 不调用远程接口，不拦截聊天请求，不发送遥测。
- 不持久化正文、摘要、对话列表、会话令牌或消息 ID。
- 摘要只用于当前页的单行显示；不建立全文索引或完整聊天副本。

内容脚本工作在扩展的隔离 JavaScript 环境中，但共享页面 DOM；这种隔离不能让 DOM 修改自动获得兼容性保证。参考 [Chrome 内容脚本文档](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)。

## 后续是否走向虚拟化

如果实测表明折叠已明显改善内存和滚动，可以先继续维护适配器和交互保护。如果主要内存仍被站点 JavaScript 状态和 DOM 持有，单纯增加折叠规则收益可能很小。

视口虚拟化的下一步必须先确定内容恢复来源、站点更新兼容性、滚动锚点以及查找体验。把节点挪到离屏 `DocumentFragment` 仍然保留节点对象，不能据此声称释放 DOM 内存；保存完整 HTML 字符串也可能增加新的内存副本。

下一阶段的判断依据应是同一真实对话上的测量结果，而不是“虚拟化”这个名称本身。

# 0.2：ChatGPT 原生轮次虚拟化调查结果

检查日期：2026-11-05（UTC）。本报告接续 [原生生命周期验证](NATIVE_LIFECYCLE.md)，依据用户提供的 `0.2.0-assets.2` 实际页面资源清单和对应公开 JavaScript 文本。

## 结论与接入决定

**已经定位到原站通过 React 裁剪轮次子树的虚拟列表，以及它到实际回答组件的调用链。当前找到的接口不支持在视口位置不变时，单独卸载一条可见回答的正文并保留可操作的折叠条。**

这完成了“是否存在真实原生卸载机制”的源码验证，但尚未建立扩展可用的逐回答卸载入口。0.2 的下一步应验证正文渲染边界或测量折叠与原生窗口的相互影响。现有导航 API、保留引用计数和 DOM 状态属性都不作为深度折叠控制器接入。

安装版本仍为 0.1.7。本次变更只记录调查结果；没有调用用户页面中的原生控制器，也没有测量内存收益或验证重新挂载后的组件局部状态。

## 原站如何卸载和重新挂载

S1 的 `if6d` 根据视口高度、距离底部的位置、各轮次测量或估计高度及累计偏移，计算连续的轮次索引范围。源码还包含窗口外渲染缓冲和范围迟滞：常规 overscan 为 2；旧范围已经覆盖新需求时，可以继续保留旧范围。因此，刚离开屏幕的回答不一定立即卸载。

它实际返回的行组件集合可以写成：

**原生挂载的轮次 = 当前渲染窗口内的轮次 ∪ 额外要求保留的轮次。**

列表先对 entries 按范围切片，再加入范围外要求保留的 entries，最后仅对这个集合创建 React 行组件。没有进入集合的轮次不会在该列表返回的 React 子树中生成行。外层保留整段列表的总高度，按累计位置放置窗口内及额外保留的轮次，从而维持滚动几何关系。

这是实际的 React 子树窗口化。滚回相应位置后，原站可以再次用原有 renderer 和数据创建行组件，不需要扩展保存 HTML 后重放。控制单位是列表 entry/turn；不能把它直接视为任意助手正文块的独立生命周期接口。

S2 到 S3 的链路已连通：会话页面 `sJ` → 对话区 `s6` → 列表调用者 `aY` → `if6d` → 行包装 `aR` → 参数转换 `aM` → 轮次 renderer `CMzj.cG`。在已检查的 `s6` 分支中，没有全屏内容、加载错误或加载状态且存在可渲染轮次时，走这条列表路径。

行 ref 清理会停止相应 ResizeObserver 观察，并删除该列表局部 Map 中的元素引用。这说明存在正常清理路径；其他持有者是否仍引用节点、垃圾回收何时发生，仍需独立验证。

## 已找到的 API 能做什么

S1 通过 `onApiChange` 交给上层的对象只有以下四个方法：

| 方法 | 已确认用途 | 能否完成“可见回答原地折叠并卸载正文” |
| --- | --- | --- |
| `getEntriesInViewport` | 查询当前视口中的 entries | 不能，只有查询能力 |
| `getEntryGeometry` | 查询条目位置和尺寸 | 不能，只有查询能力 |
| `measureTurnBeforePaint` | 请求／协调轮次高度测量 | 不能，没有按回答排除正文的控制项 |
| `scrollToKey` | 让目标进入对应窗口并滚动定位 | 不能，它会移动滚动位置 |

S2 将该对象保存在 `s6` 的私有 React state 中，再通过私有 ref 向父组件提供 `scrollToMessage()`。在这条已检查的调用链中，没有发现对扩展公开的逐回答卸载方法或页面事件桥。模块有 export 不代表扩展已取得对应的存活组件实例、scope 或控制权限。

这组方法可作为未来按需定位的研究线索。它仍需运行时实例和兼容性验证，且用户已将查找定位功能暂缓，因此本阶段不开发导航接入。

没有发现可见轮次的排除集合、逐条正文的挂载开关或保留空壳的 setter。此结论限于本次追踪的模块、接口和调用路径，不声称所有未加载模块或其他部署版本都不存在这样的能力。

## 为什么保留／解除保留不能用于折叠

S1 的 `g3o5` 对 key 维护引用计数。调用方取得一个保留句柄，清理时释放自己的计数；列表再把这些 key 与 `retainedTurnKeys` 参数合并。S8 确认它使用 `AppScope`，但本次没有验证实际 provider 实例的生命周期，不能扩展为跨标签页共享。

保留机制的含义是“即使离开窗口也继续挂载”。解除保留只取消该持有方的额外要求，无法从视口范围切片中排除仍然可见的轮次。清空其他持有方的计数既违反其所有权，也不能解决这个问题。

因此，0.1.x 的手动展开意图仍应是有界的轻量状态。回答滚出窗口后可以让原站正常卸载；重新出现时再恢复用户期望的展开状态。若把“用户手动展开过”映射成永久保留真实 DOM，会增加离屏占用，与内存优先目标冲突。

## 三类容易混淆的机制

### DOM 状态标记

S3 的 `data-talvt-turn-state` 由派生轮次状态输出，S4 读取它用于绘制和可见性观测。该属性没有在这条链路中构成挂载控制输入。改写属性不能据此触发原生卸载。

S9 的 `[data-turn-key]` 命中属于短时滚动锚定辅助逻辑；它在布局变化后调整滚动位置，不负责选择渲染集合。

### CSS 渲染跳过

S5 的 `OF8q` 给单项内容添加 `content-visibility:auto` 和固有高度估计，但仍传入原来的 children。多项分支交给 S6 的 `GRDa`，后者只是普通布局组件。原生窗口列表的行包装还会把相应后代的 content visibility 强制设为 visible。

这些 CSS 包装不能证明 DOM 或组件数据已释放。它们与上面选择 React 行集合的虚拟列表是不同层次的机制。

### 原生活动／思考详情折叠

S6 的 `r9ev` 有 `unmountOnCollapse` 参数，默认 false。默认路径用高度、透明度和 inert 处理折叠，仍保留 children；启用该参数时会转入 S7 的 `tnfs`，后者根据展开状态条件输出子组件，并经过退出动画处理。

在这 86 份文本中，该参数字面名称只出现在定义处，没有直接设置为 true 的调用点。这不排除间接传参或其他资源使用它。它说明原站存在通用的条件移除组件，但没有证明用户看到的每种思考折叠都会卸载，也没有提供完整回答的按 ID 控制接口。

## 对内存目标的实际含义

源码证明原站能控制渲染子树的规模，但整个对话的数据、entries 数组、数值高度缓存和其他持有者仍可能存在。卸载子树提供释放部分 DOM、组件和附属对象的机会；不能从静态源码推导出固定节省比例、总内存上限或永不崩溃。

**待实测推论：折叠高度可能与原站窗口化发生反向作用。** 当前扩展把多个回答压成较矮的折叠条。如果原站测量值随之降低，同一窗口可能包含更多轮次；那些被 CSS 隐藏的正文仍可能随行挂载。结果可能是渲染工作减少，但同时挂载的轮次数增加。末条最小高度、overscan、范围迟滞和高度更新时机都会影响结果，不能只用折叠条高度估算内存增减。

因此后续首先应比较同一会话、同一位置和相同稳定阶段下启用／暂停折叠时的挂载轮次数、连接的 DOM 规模以及内存，记录是否正在生成，并重复采样。标签页总内存和 JS 堆需分开判断；单次 DOM 计数、WeakRef 状态或 `performance.memory` 读数不能单独证明净收益。探针和 DevTools 自身的引用也应控制。

## 0.2 后续验证边界

如果继续保留原生回答组件，真正需要验证的是：能否在原生行或正文 renderer 的输入边界增加可控的条件挂载，同时留下稳定、轻量的折叠宿主。它至少需要满足：

1. 目标仍在屏幕内时，仅正文从原生组件树移除，折叠条和相邻轮次不受影响。
2. 展开后原站创建正文，复制、代码、引用及其他原生交互可用；局部组件状态的恢复语义需单独说明。
3. 正在生成的最新回答持续展开，手动展开意图仍遵守上限，离屏 DOM 不因保存意图而常驻。
4. 原站改变结构或接口后能回退到现有折叠；不依赖覆盖 DOM 输出标记或清理他人的保留计数。
5. 重复折叠、展开、滚动和生成后，测得内存净收益且没有不断累积的引用。

这比调用已有导航方法需要更深入的私有渲染器适配。当前证据足以排除“找到保留函数就能立即接入深度折叠”的方案，尚不足以给出可靠、低侵入的正文卸载实现。

本阶段不要求用户重新采集资源或设置 DOM 断点。已有材料足够完成这次机制判断；后续实验应针对明确的渲染边界或内存假设设计。

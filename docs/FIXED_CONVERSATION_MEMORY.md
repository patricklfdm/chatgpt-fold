# 固定会话：比较扩展开启与关闭时的进程内存

这项实验比较**同一段已完成的对话、同一段浏览路线**下，ChatGPT Fold 开启和完全停用时的进程内存。全程不增加消息；脚本提示何时切换、静置、翻阅和复核。它接续[长会话记录](LONG_SESSION_MEMORY.md)，用来补充单一配置下无法回答的开关差异。

安装版本仍为 **0.1.7**。这是独立的本地研究脚本，不加入扩展清单，也不调用网页的原生卸载控制器。

## 运行前准备

适用于 **Windows 或 Linux 桌面、Node.js 20+**。在运行 Chrome 的同一台电脑上，用 VS Code 打开已更新的仓库。脚本没有第三方依赖，**无需 `npm install`**。Windows 使用原生 PowerShell 或命令提示符；WSL、远程机器或容器中的 PID 不能用来选取桌面 Chrome。

1. 选一段已经生成完毕的长对话，停在**最新回答末尾**。四轮都使用这段会话，保持窗口尺寸、缩放和其他扩展设置一致。
2. 选定一条较早的回答作为翻阅端点，可以用它前面的用户提问辨认。每轮从最新回答出发，向上浏览到这条回答，再回到同一条最新回答的末尾。端点只需自己记住，**不要把对话正文、消息 ID 或网址输入脚本**。
3. 设定好日常使用的折叠偏好。开启条件要求 Chrome 中的扩展已启用，扩展内的自动折叠也开启，且本页未处于临时恢复状态。两次开启条件保持相同偏好，测试时不额外点击展开、编辑或重新生成。
4. 打开 **Chrome 自己的任务管理器**：Chrome 菜单 → **更多工具 → 任务管理器**。`Shift+Esc` 可用时也可以用快捷键。右键表头显示「**进程 ID / Process ID**」，找到目标 ChatGPT **标签页**那一行。不要选择 Browser、GPU、Extension 或 Subframe 行，也不要复制整行标题。

折叠会改变页面高度，**不能把“各向上滑三屏”当成相同路线**。四轮应经过同一批历史回答，尽量采用相近的滚动速度和停留时间；直接跳到端点不能替代浏览过程。可在正式开始前确认一次端点，再按脚本要求重新加载开始首轮。

## 启动与四轮操作

在仓库根目录的终端运行：

```sh
node experiments/fixed-conversation-memory.cjs
```

也可以运行 `npm run study:compare`。Windows PowerShell 若阻止执行 `npm.ps1`，直接用上面的 `node` 命令，或用 `npm.cmd run study:compare`；无需修改执行策略。

脚本按下面的固定顺序引导四轮：

| 轮次 | Chrome 中的 ChatGPT Fold 状态 | 准备好后在终端输入 |
| --- | --- | --- |
| 1 | 开启，自动折叠生效 | `on 进程ID` |
| 2 | 完全停用 | `off 进程ID` |
| 3 | 继续完全停用，再重新加载一次页面 | `off 进程ID` |
| 4 | 重新开启，恢复同一组折叠设置 | `on 进程ID` |

例如脚本要求开启条件、当前 PID 为 `12345` 时，输入 `on 12345`。PID 必须使用这次实际看到的数字。**每轮都先重新加载同一 ChatGPT 标签页，再确认 PID 和末尾位置**；跨轮 PID 可以不同。

“完全停用”指在 Chrome 地址栏打开 `chrome://extensions`，关闭 **ChatGPT Fold 卡片上的总开关**，然后重新加载目标 ChatGPT 页。只关闭扩展弹窗里的自动折叠，或选择临时恢复本页，仍可能留下扩展自身的工作，不能作为这里的完全停用条件。

每轮按终端提示做三件事：

1. **准备并开始。** 设置本轮开关状态，重新加载同一对话，等生成结束并回到最新回答末尾。确认 Chrome 任务管理器的目标标签 PID，输入本轮的 `on PID` 或 `off PID`。切回 Chrome，保持不操作：先预留约 **30 秒**，再采 **20 秒**翻阅前窗口。见到「翻阅」提示再继续。
2. **浏览固定路线并返回。** 向上经过约定的历史内容，到达事先选定的回答，再回到刚才同一条最新回答末尾。期间不新增消息。回到末尾后在终端**直接回车**，再切回 Chrome，保持约 **23 秒**不操作：其中 3 秒用于切换窗口，随后采 20 秒返回窗口。
3. **复核并进入下一轮。** 脚本暂停采样后，再看 Chrome 任务管理器中同一标签行的 PID。只有确认本轮内容未变、实际走过约定路线并回到相同末尾时，才输入现在看到的数字。无法确认则直接回车，停止此次对照并保留读数；已知内容、路线或页面状态发生偏离，输入 `x` 结束。复核等待不计入本轮的测量时长和峰值。

每轮之间按提示重新加载；一轮开始采样后不刷新、切换会话或改变扩展设置。脚本只读取你指定的进程计数，**不会自动识别扩展开关、浏览位置或是否真的走过同一条路线**，这些条件由操作者确认。

完成四轮后，扩展应处于开启条件。脚本会显示输出目录，**只需提供本次 `summary.json`**，不必复制所有采样或任务管理器截图。

### 提前停止或操作有误

- 输入 `q` 立即结束，保留已经采到的结果，不再要求复核。四轮未全部完成时，不生成完整的开关配对差值。
- 一轮内发生刷新、切换会话、新增或修改消息、走错路线、进程迁移等已知偏离时，输入 `x`。已有读数可保留，但不把偏离前后拼成合格对照。
- 目标退出、身份变化或无法读取时，记录器停止，不自动改采其他 PID。首尾 PID 相同也不能发现所有页面重载或先换走再换回的情况。
- 末次输入的 PID 与本轮开始时不同，或两分钟内未完成复核，记录器停止并保留部分结果，不继续下一轮。
- 如果在停用阶段提前结束，按日常偏好重新开启扩展并刷新页面；脚本只提示切换，不会替你操作扩展开关。

## 怎样读结果

每秒尝试读取一次所选进程。Windows 主指标是 **Private Bytes（私有提交内存）**，Linux 是 **RssAnon + VmSwap**；同时记录工作集或驻留集作辅助。指标定义、官方来源和跨平台差异见[计数口径说明](LONG_SESSION_MEMORY.md#windowslinux-和-chrome-任务管理器的口径)。主指标、工作集和 JavaScript 堆不能相加；本工具没有测量 JavaScript 堆或整个标签页涉及的全部进程。

先查看各轮完成状态、末次 PID 复核和采样覆盖，再比较数值：

各轮数据在 `runs`；汇总在 `comparison`。`pairedDifferencesAvailable` 只说明前后窗口的配对条件通过，`scrollPeakDifferencesAvailable` 单独表示翻阅峰值差是否可用；它们都不表示已经证明省内存。

| 记录 | 用途与解释 |
| --- | --- |
| 每轮 `pre` / `post` 中位数 | 翻阅前与返回后的 20 秒窗口；位置和内容相同由操作者确认 |
| 窗口最小值、最大值、范围及前后半段中位数 | 检查窗口内波动；样本完整并不表示内存已经稳定 |
| 每轮 `scroll` 峰值、时长和采样覆盖 | 浏览固定历史路线时实际采到的最高值；不同操作时长可能改变捕捉峰值的机会 |
| 每轮返回后减翻阅前 | 同一轮浏览往返后的变化；自然回收、缓存和后台活动仍可能影响结果 |
| 第 1 轮开启 − 第 2 轮关闭；第 4 轮开启 − 第 3 轮关闭 | 两次方向统一的开关差值：负数表示该指标在开启时较低，正数表示较高 |
| 同一条件两次结果之间的差距 | 判断开关差异是否大于重复运行本身的波动 |

四轮须满足顺序、同一指标、相同采样时序、完整有效的采样窗口，以及每轮内末次 PID 核对一致等条件，才提供完整的配对差值。不满足时保留各轮描述性结果，相关差值为 `null`，不以零替代。翻阅阶段的峰值差还单独检查该阶段的采样覆盖；这部分有缺口时，峰值差可为 `null`，而合格的前后窗口差仍可保留。报告不会把负差值自动解释成已证实的省内存百分比。

`valid` 和采样覆盖表示读数数量、间隔和窗口完成情况符合要求。即使全部有效，一个窗口也可能处于上升或回落过程中；应同时检查最小值、最大值和前后半段变化。每秒采样得到的峰值可能漏掉更短的尖峰，也不等于进程整个生命周期的系统峰值。

这项对照采用**开启 → 关闭 → 关闭 → 开启**，用于观察顺序反转后差异能否重复。普通重新加载不保证创建新进程，也不保证清空缓存；平衡顺序只能减弱部分顺序影响。相同进程可能承载其他页面，其他标签和后台活动也应尽量保持一致。两次差值方向一致仍不等于已排除所有混淆因素。

若开关差异小于窗口波动或重复运行差距，结果应表述为**暂未检出明确净收益**。该结论不等于扩展完全无效。即使观察到可重复的较低占用，也只适用于这段会话和浏览任务，不能由此承诺长时间生成不会崩溃。

## 输出与数据范围

每次启动创建新的 `artifacts/fixed-conversation/run-*/` 目录，不覆盖此前实验。`summary.json` 保存汇总；`trace.jsonl` 保存本地的相对时间、轮次、条件、阶段和数值计数。异常结束时可能仅有部分数据或上一次检查点，不应当作完整对照。输出目录已由仓库忽略。

PID 仅在本机用于选取和核验进程，不写入结果文件。记录器不读取对话、DOM、网址、窗口标题、命令行或剪贴板，不上传结果、不强制垃圾回收，也不需要 DevTools 或新增扩展权限。页面内容和浏览条件始终是操作者声明，不能把这份进程报告当作网页状态验证。

## macOS 或手工记录

macOS 暂无自动读取器。可以按相同四轮顺序，在 Chrome 自己的任务管理器手记：**轮次、开启／关闭、翻阅前读数、返回后读数、浏览时亲眼见到的最高值、单位，以及本轮首尾 PID 是否相同**。不要提交 PID 数字、标签标题或整页截图。保持相同路线、窗口尺寸和等待时间，注明是手工数据；手记单点不能冒充 20 秒窗口中位数或连续采样峰值。任务管理器字段的说明见[Chrome 官方文档](https://developer.chrome.com/docs/devtools/memory-problems#monitor-memory-use-in-realtime-with-the-chrome-task-manager)。

## 开发验证

- `npm run test:comparison`：25 项统计和真实终端控制器的测试，使用模拟时钟和计数读取器，覆盖顺序反转、窗口波动、缺采、阶段边界、复核超时、进程错误、提前退出及资源清理。
- `node tests/fixed-conversation-chromium.cjs`：独立 Linux Chromium、离线合成页面、实际 0.1.7 内容脚本及隔离世界内模拟 Chrome API。它驱动实际终端控制器与 OS 计数读取器，验证四次加载的 48 条回答内容一致、同一历史回答往返路线、开关布局效果及每轮读取器清理。需 Playwright 和 Chromium；嵌套 PID 测试容器另需 Python 3 的 `os.pidfd_open`。
- 本次 Chromium 153 验证采用缩短的采样时序，取得 117 个真实进程样本，8 个尾部窗口有效，4 个读取器均已关闭。它验证记录流程，不代表真实 ChatGPT 页面、Windows 内存水平或扩展的净收益。
- Windows CI 同时运行本对照和原长会话的统计／流程测试，并复用已有的 Windows 进程计数及退出检查。

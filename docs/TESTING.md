# 测试与验收

本文列出检查方法、预期行为和记录模板。**这些步骤不代表已经在你的 Chrome 或真实 ChatGPT 会话中执行。** 模拟页面通过也不能证明当前线上页面完全兼容。

## 检查层次

| 层次 | 检查内容 | 不能证明什么 |
| --- | --- | --- |
| 静态检查 | JavaScript 语法、清单与工程完整性 | 真实 DOM 匹配、交互和节省内存 |
| Node 测试 | 配置与可独立测试的逻辑 | Chrome 注入行为和实际页面兼容性 |
| DOM 适配器回归 | Linkedom 合成 HTML 上的角色识别、冲突过滤、扫描范围与诊断字段 | Chrome 观察器时序、扩展注入、布局或真实 ChatGPT 结构 |
| 合成页面浏览器测试 | 受控 DOM 上的折叠、恢复和动态行为 | 线上生成状态、所有富内容和网站未来更新 |
| 第一帧浏览器回归 | 历史回答挂载或更新后，以及思考 / 生成阶段，下一次绘制机会的显示、按钮和徽标状态 | 扩展冷启动之前的画面、尚无作者标记的结构和真实页面内存收益 |
| 展开状态浏览器回归 | 同一消息重挂载、追加新回答、名额与淘汰顺序，以及明确重置 | 所有线上消息身份形式、真实 MV3 注入和内存节省比例 |
| 维护浏览器回归 | body 自动清理与恢复、暂停 / 挂起、待处理队列、普通更新调用范围及语义回退 | 真实站点全部更新形式、长期内存上限或总内存节省 |
| 合成内存与开销基准 | 固定内容下的 DOM / 布局 / 堆指标、窗口卸载趋势、普通生成更新的调用量 | 真实 ChatGPT 的数据保留、图片与 GPU、整个标签页总占用 |
| 真实页面手动验收 | 你的实际对话、模型输出和站点交互 | 所有账户、所有地区、所有未来版本 |
| 内存对照实验 | 指定环境与对话下的实际收益 | 对所有长对话都成立的节省比例 |

## 自动检查

在工程根目录运行：

```bash
npm test
npm run check
```

这两项使用 Node.js 20 或更新版本和工程自带脚本，不需要 npm 安装第三方依赖。

可选的 DOM 识别回归：

```bash
npm install --no-save --package-lock=false linkedom@0.18.15
npm run test:dom
```

`tests/adapter-dom.cjs` 通过 Linkedom 解析合成 HTML，并运行项目实际的适配器代码。它检查候选回答、用户角色冲突、嵌套去重、语义祖先扫描范围及诊断内容，不模拟选择器实现，也不等同于真实浏览器测试。缺少依赖时入口返回 **NOT RUN / 退出码 2**。

可选浏览器检查：

```bash
npm install --no-save playwright
npx playwright install chromium
npm run test:browser
```

浏览器检查使用 `tests/fixtures/chat.html` 的合成内容。测试浏览器与真实个人 Chrome 的登录状态、扩展安装和线上 ChatGPT 页面相互独立。

默认模式加载真实的未打包扩展，检查扩展运行流程。还可以显式运行注入模式：

```bash
npm run test:browser -- --mode=injected
```

注入模式在真实 Chromium 中执行实际页面脚本与 CSS，可以验证 `MutationObserver`、布局隐藏与页面交互，但 Chrome 扩展 API 由测试脚本模拟，不能验证真实权限、隔离世界注入或扩展消息管道。每次结果应同时记录版本、模式和实际运行的组数，详见 [VALIDATION.md](VALIDATION.md)。

针对历史回答闪现和思考阶段误锁旧回答的问题，运行：

```bash
npm run test:paint
```

`tests/browser-first-paint.cjs` 仅使用明确标注的注入模式和模拟 Chrome API。它在页面修改 DOM 后的下一次 `requestAnimationFrame` 读取实际计算样式、布局盒和控制栏状态，并继续采样后续帧。断言期间不调用状态查询、`flush()` 或重新扫描，避免这些操作替控制器完成折叠而掩盖时序缺陷。内容均为合成数据，网络请求被拦截；不读取真实会话。

第一帧测试覆盖历史重新挂载、已折叠正文补齐和替换、消息身份变化、隐藏时间线激活、历史窗口连续变化、已知末尾重新挂载后的正常新增、生成标记与原生 CSS 隐藏冲突，以及暂停 / 禁用后的原内容可见性。通过这些测试不能证明内容脚本初始化前也没有展开画面。

0.1.5 还检查 Stop 先于新问题 / 回答出现、新问题先于 Stop 出现、思考阶段取消、历史窗口变化、局部重新生成、目标身份补齐与重新挂载，以及下一次请求重新确定目标。除正文可见性外，还在首帧断言折叠按钮是否可用、徽标是否误显示“生成中”。

针对展开选择保留和追加回答，运行：

```bash
npm run test:state
```

`tests/browser-open-state.cjs` 同样使用真实 Chromium、合成内容与模拟 Chrome API。它通过页面控件建立展开选择，在卸载、重新挂载或追加回答后的第一帧检查实际状态，断言期间不查询扩展状态或调用重扫。测试覆盖未超上限时保留 A、B 并加入 C、超限时淘汰最早展开项、已卸载项的名额与淘汰、明确收起 / 重置、对话隔离，以及生成保护不转成长期展开选择。

消息身份场景还包括内部消息标识容器、重复 / 冲突身份、节点换成另一条消息，以及只有位置型 unit key 的新节点不能继承展开选择。同一活动节点晚到的实际 ID，只有在临时身份提示未变时才接续原选择。记住“它是助手回答”和确认“它是原来那条回答”需要分别验证。

针对 0.1.6 的清理与普通更新路径，运行：

```bash
npm run test:maintenance
```

`tests/browser-maintenance.cjs` 使用真实 Chromium 与模拟 Chrome API，在合成页面中验证 body 替换后的自动恢复、暂时没有 body 时的后续恢复、同路由展开选择，以及暂停、禁用、pagehide 和销毁后的停止。清理断言直接观察 DOM 与集合的数字，不调用状态请求或手动重扫来帮助修复。还检查重复窗口移除、待处理队列上限，以及控制栏修复不会被批次执行前的点击或设置变化吞掉。

普通更新用例在控制器加载前包装适配器入口，页面稳定后才开始计数，检查文字 / 普通代码标记更新不会扫描所有历史身份、候选和全局生成状态。新增 / 移除内部消息 ID、非助手角色、生成标记、裸文本与交互等用例验证完整检查仍生效。这些断言检查实现行为与工作范围，不设置运行时间或内存字节阈值。

可重复的合成内存与更新开销测量：

```bash
npm run bench:memory -- --quick --output artifacts/memory/smoke.json
npm run bench:memory -- --output artifacts/memory/current.json
```

`--quick` 用于检查基准可运行；默认完整配置进行 3 次独立重复，覆盖完整挂载、固定 20 条窗口累计 1200 条，以及普通生成内容更新。可以通过 `--compare` 指定旧版本工作树。JSON 会记录源码哈希、GC 前后指标与完成状态，缺失指标为 `null`。具体参数、指标含义和复现方法见 [MEMORY.md](MEMORY.md)。

如果当前执行环境无法安装或启动 Chromium，应记录为“未执行 / 环境阻塞”，不能把它写成通过。

## 真实页面手动验收

先只启用 ChatGPT Fold，暂时关闭其他折叠、隐藏或重排对话的扩展。加载最新源码后，在 `chrome://extensions` 重新加载扩展，再刷新 ChatGPT 标签页。

修复 PR 合并后，在原安装仓库更新 `main` 分支；不要同时加载两份扩展。重新加载扩展并刷新页面后，打开弹窗确认版本为 **0.1.6**。

### 1. 首次进入长对话

1. 使用一段已有多轮助手回答的对话。
2. 打开扩展弹窗，确认启用、默认最近数量为 1、同时展开上限为 1。
3. 等待页面加载稳定，观察每条支持的助手回答。

预期：

- 用户问题仍完整显示。
- 支持的助手回答都有单行摘要与可操作按钮。
- 最新 1 条普通回答展开，其余普通回答折叠。
- 输入框、侧栏、导航和原有对话功能正常。
- 弹窗统计与页面状态相符；已识别但结构不支持时保留内容并报告未支持数量。完全缺少支持的角色标记时，应显示已识别 0 条并保留页面原样。

### 2. 展开与数量上限

1. 展开一条较旧回答。
2. 展开另一条较旧回答。
3. 收起当前回答。
4. 将上限改为 2，再展开两条普通回答。

预期：每次操作后，未受保护的展开回答数量不超过设置上限；再次点击可以收起。折叠 / 展开后，鼠标和键盘仍能操作控件。

### 3. 设置边界

分别验证最近数量 0、1、5，以及上限 1、2、5。尝试输入空值、负数、小数或超大值（如果控件允许），然后保存。

预期：无效输入被约束到有效范围；默认最近数量不大于上限；关闭后重新打开弹窗、刷新页面，偏好仍保留。聊天正文不应出现在 `chrome.storage.local`。

仅修改同时展开上限时，仍在限额内的展开选择应保留。降低上限会移除最早的选择，提高上限不会重新打开已淘汰项。修改默认最近数量会按当前已挂载回答重新应用默认策略。

### 4. 正在生成

1. 保持折叠开启，发送一个会产生多段回答的普通问题。
2. 回答生成期间打开其他旧回答，尝试批量收起。
3. 等待生成结束，重复展开和收起。

预期：识别到的正在生成回答暂时保持展开；原站停止生成、继续生成和复制等功能保持正常。保护期间可以临时超过数量上限，结束后重新应用策略。新回答出现前的思考阶段另按[生成目标验收](#14-思考期间的生成目标)检查，不能把上一条已完成回答当作生成目标。

记录使用的生成入口和页面表现。若保护未识别到，应记录 DOM 适配问题，不要把长回答误认为“正常可折叠的旧回答”。

### 5. 文字选择与编辑

1. 在展开的助手回答中选择一段正文。
2. 保持选区，打开另一条回答或执行批量收起。
3. 清除选区，重复操作。
4. 在原站可编辑的区域进入编辑状态，验证输入、取消和保存。

预期：包含有效选区或编辑状态的回答暂时受到保护；不丢失选区或编辑内容；保护结束后可重新折叠。若当前页面没有可用的回答编辑入口，将该项标为“不适用”，不要伪造测试。

### 6. 内容类型

用已有的普通文本、长列表、表格、代码块、公式和图片回答分别展开 / 收起。

预期：内容恢复后显示正确，代码复制等原站操作可用；摘要保持单行，不因长链接或代码撑宽页面。未知富内容结构应保守保留显示。

### 7. 对话切换与动态内容

1. 从侧栏切换到另一段已有对话。
2. 新建对话并连续进行多轮交流。
3. 使用浏览器前进 / 后退。
4. 如账户界面提供回答分支切换，验证不同分支。
5. 删除或重新生成一条回答后，检查状态。

预期：新页面正确识别，不残留旧对话摘要或展开选择；同一条回答不重复添加控件；页面移除的回答不继续计入当前 DOM 数量；原站操作不报错。同一对话内暂时卸载的展开选择仍占名额，切换到另一对话时才清理该会话选择。

### 8. 临时恢复与原生搜索

1. 先确认一条旧回答处于折叠状态。
2. 在扩展弹窗中临时恢复本页。
3. 使用 `Ctrl+F` / `⌘F` 搜索该回答中的词。
4. 完成阅读后继续折叠。

预期：恢复后可以搜索正文；恢复期间暂停自动折叠；继续折叠后按当前设置重新初始化选择。临时恢复会清理此前的展开选择，也会重新增加同时渲染的内容。

### 9. 禁用、刷新和异常状态

1. 在弹窗中关闭启用开关，确认原内容恢复。
2. 重新开启，确认策略恢复。
3. 打开非 ChatGPT 标签页，再打开弹窗。
4. 重载扩展但尚未刷新 ChatGPT 页面时，检查弹窗提示；随后刷新页面重试。
5. 查看 `chrome://extensions` 的扩展错误，以及页面控制台是否出现与扩展有关的异常。

预期：不可用页面有明确提示；没有消息接收端时不会显示虚假的操作成功；刷新后恢复正常。

### 10. 零识别、重新扫描与诊断

1. 在已有回答的页面上打开弹窗，记录已识别数量。若为 0，点击 **重新扫描**，无需发送新消息。
2. 点击 **查看诊断**，确认报告为 `schemaVersion: 3`，包含版本、状态、旧标记计数、`modern` 新标记计数和 `maintenance` 固定运行字段。
3. 点击 **复制报告**；若浏览器未允许复制，确认能手动复制已选中的报告文本。
4. 临时恢复本页后执行重新扫描，再关闭自动折叠后执行重新扫描。

预期：

- 已识别为 0 时，弹窗提示排查，不承诺新消息一定解决问题。
- 重新扫描不会自动解除本页暂停或重新打开全局开关。
- 报告不含正文、摘要、HTML、标题、URL、消息 ID、任意类名或未知角色原值；关闭弹窗后不持久保存报告。
- 与当前内容脚本版本不一致时，弹窗明确要求刷新页面。

报告中的 `eligibleAnswerCount` 是按当前结构规则发现的数量；`registeredAnswerCount` 是控制器实际登记数量。只有 `active: true` 时，二者的差异才可能提示跟踪遗漏；暂停或关闭时没有登记记录是正常行为。旧版角色 / turn 计数为 0 时，应同时查看 `modern.searchUnitAssistantCount`、`modern.contentUnitAssistantCount`、`modern.messageRoleAssistantCount` 和 `modern.assistantBodyCount`。同一回答可能贡献多个原始标记，不能把这些计数相加作为回答总数。

所有已支持助手标记都为 0 时，仍需核对实际内容位置与结构；一个 iframe 的存在不能单独证明回答位于其中。`modern.inactiveCandidateCount` 表示按当前显示规则排除的候选，可能帮助识别隐藏工作区或副本。

合成浏览器回归还覆盖去掉内层角色属性、仅删除角色节点、非 `article` 助手 turn 和用户角色冲突。旧的同路由 body 替换后重扫用例继续保留；0.1.6 的独立维护回归进一步检查不借助重扫、状态或交互的自动清理与首帧恢复，以及 body 暂时缺失后的重新连接。这些场景用于检查实现缺陷，不需要在自己的真实聊天页面手动修改 DOM。

### 11. 新版消息单元与工作区

在使用新版页面结构的真实会话中，重点检查：

- **用户提问保持可见。** 收起全部后，用户气泡和输入框应保留；一个轮次包含提问与回答时，只处理明确的助手部分。
- **一条回答只有一个有效控制栏。** 同时存在两种 unit key、正文标记或重复消息标识时，不应重复添加栏位；正文与原生复制按钮仍可使用。
- **仅统计当前活动内容。** 从侧栏切换对话后，隐藏的旧工作区不应继续占据展开名额。回到原会话时重新应用当前偏好。
- **生成保护对应实际回答并及时解除。** 输入区中的 Stop / 停止按钮出现后，已确认新增的回答保留展开；尚无新回答时旧回答仍可操作。完成后按普通回答策略处理。回答里的普通同名按钮不应让整页持续保持生成状态。
- **屏幕外内容不被当成隐藏副本。** 本版不是视口虚拟化；活动文档中已挂载但位于屏幕外的回答仍可识别。站点若自行卸载与重新挂载内容，统计随当前 DOM 变化，不代表服务端聊天记录丢失。

合成用例还应验证单独的 turn / 状态 / 消息 ID 不产生助手身份、冲突标识或多个不同消息 ID 不推广为整个回答、身份一致的多段正文保持一个折叠项、无可靠分组依据的多个裸正文片段保持原样、角色属性单独变化能重新发现、隐藏副本切换、`display:contents` 容器和普通样式更新。实际已执行范围以 [VALIDATION.md](VALIDATION.md) 为准。

### 12. 快速浏览历史回答

1. 先等待扩展启动并确认已有回答正常折叠，设置默认最近 1 条、上限 1。
2. 从对话末尾快速向上翻阅多屏，再向下返回，重复经过同一批旧回答。观察正文首次进入视野的画面，而不只看滚动停止后的状态。
3. 手动展开一条旧回答，再翻阅邻近历史内容，检查其他旧回答是否无故展开或抢占名额。
4. 将默认最近数量设为 0，重复快速翻阅；完成后按需恢复设置。
5. 在此设置下发起一次正常生成，确认新回答仍及时显示，结束后遵守折叠策略。临时恢复本页或关闭折叠后，确认旧内容恢复可见。

预期：未选择展开的历史回答重新挂载或补齐正文时，直接呈现摘要，不出现全文先展开再收起的过程；仍有效的展开选择则直接恢复展开。生成、选区和原生焦点保护保持有效。页面若卸载实际末尾回答，剩余窗口的最后一项不应仅因此自动展开。

如果身份不足以恢复某项展开选择，或不足以确认插入的是新回答，扩展不会按位置猜测。需要时可手动展开，或点击“展开最近”按当前已挂载内容重新应用偏好；这不代表回答数据丢失。

如果仍有闪现，记录扩展版本、设置、发生在首次加载还是稳定浏览中，以及是否只在某种回答内容或分支切换时出现。可用经过隐私处理的短录屏辅助定位；无需把对话正文或完整 HTML 发出。内容脚本启动前和页面尚未提供可靠作者标记时的显示，不属于本次第一帧回归覆盖范围。

### 13. 保留展开选择与追加新回答

1. 在同一段长对话中设置默认最近 1 条、同时展开上限 3。收起其他普通回答，再依次手动展开 A、B；确认没有生成、文字选区或编辑焦点保护干扰观察。
2. 滚动到足够远的位置，再回到 A、B。站点可能已经卸载并重新创建节点，但能可靠识别的 A、B 应仍然展开，不能因为滚动把它们视为新选择。
3. 在这段对话中发起新回答 C。生成结束后，A、B、C 应都保留展开；总数未超 3 时不收起 A 或 B。
4. 再展开另一条回答 D。此时才移除最早展开的 A；即使 A 当时已被站点卸载，返回查看它也应保持折叠。随后收起 D 腾出名额，A 仍不应自动打开。
5. 重新建立几项选择，只降低同时展开上限，再提高上限。仍在名额内的较新选择应保留，被淘汰的项不会恢复；不应重新套用默认最近数量而收起所有旧选择。
6. 点击“收起全部”，滚动返回此前展开过的旧回答；它们应保持折叠。点击“展开最近”则明确重设选择，不保留此前已卸载的展开项。

另行验证默认最近数量为 0 的情况：修改设置后手动展开 A，再正常生成一条新回答。生成期间新内容应可见；结束后新回答恢复折叠，A 保留展开。临时生成保护不应留下新的长期展开选择。

预期的记忆范围是当前页面、当前对话。刷新、切换到另一段对话、临时恢复或禁用后重新启用时，应重新应用偏好。没有可靠消息 ID、存在冲突身份或只有 `fallback-turn-N` 等位置标记的新节点，不能保证恢复展开；不要通过保存全文、序列化 HTML 或强留旧节点来满足这项验收。

### 14. 思考期间的生成目标

1. 将默认最近数量设为 1、同时展开上限设为 3。在已有对话中展开最后一条已完成回答 A，清除文字选区并离开原生编辑控件。
2. 发送新问题，在 ChatGPT 思考、尚未显示新回答正文时查看 A。A 不应仅因输入区出现停止按钮而显示“生成中”；它应保持原展开选择，且可以手动收起和再次展开。
3. 等实际新回答 B 出现，检查生成保护属于 B，A 仍可操作。生成结束后，B 的按钮恢复可用；A 与 B 未超过上限时都保留展开。
4. 再发送一个问题，在新回答尚未出现前取消。已有回答不应被锁住，也不应因这次取消留下“生成中”状态。再次发起请求时，上一轮回答不能直接继承新的生成保护。
5. 思考等待期间上下翻阅历史，再回到末尾。历史回答被卸载 / 重新挂载后，不应变成全局停止按钮的替代目标；已有展开选择仍按原规则恢复。
6. 将默认最近数量改为 0，手动展开 A，再发起一次正常生成。新回答生成期间应保持可见，结束后恢复折叠；A 的选择不因临时保护而丢失。

另行测试原站“重新生成”入口：页面若提供明确的回答局部生成标记，只保护对应回答，不额外锁住其他最后一条回答。仅有全局停止按钮而没有可确认目标时，沿用普通展开策略；扩展启动 / 恢复时回答已存在且只有全局 Stop、回答容器先于 Stop 登记等边界见[架构说明](ARCHITECTURE.md#无法仅靠停止按钮确认的情况)。记录具体入口与表现，不能把缺少目标证据写成已验证生成保护。

### 15. 维护与持续更新诊断

1. 正常打开一段已有对话，等待页面稳定，查看一次诊断并记录 `maintenance` 数值。无需为测量展开全部历史。
2. 关闭弹窗，正常生成一条包含段落或代码的回答；结束后重新打开诊断比较累计工作计数。继续验证已有展开选择、生成结束后的按钮和最终摘要。
3. 上下浏览若干屏历史，再切换到另一段对话并返回；稳定后查看当前登记数量、`disconnectedRegisteredCount` 与队列长度。
4. 临时恢复本页、关闭自动折叠，再分别查看诊断。按需要继续折叠或重新开启，检查观察器与控制栏正常恢复。

预期与解释：

- 正常活动页面上，内容观察器和 body 观察器均连接；稳定后 `maintenance.disconnectedRegisteredCount` 为 0，两个待处理队列通常为 0。暂停或禁用后观察器断开、当前记录与队列清空。
- `openIntentCount` 不超过当前设置上限，可能包括暂时卸载的回答；它不要求等于当前 DOM 的已展开数量。
- 普通内容批次可增加 `incrementalFlushCount`；真实生成还可能改变语义标记、身份或结构，因而 `fullFlushCount` 增加并不代表优化失败。不能要求每个生成 token 都对应一次增量批次。
- `releasedRecordCount` 会因正常卸载、切换对话、暂停和禁用增长，不是泄漏计数。`bodyReplacementCount` 只有实际观察到活动 body 替换或移除时才增长；普通使用没有发生此事件时为 0 很正常。
- 工作计数属于当前内容脚本实例，不因打开或关闭弹窗而重置；刷新页面后重新开始。诊断先消化待处理工作再返回，不能用几次快照重建全部更新历史。

如果已断开记录在稳定后仍不为 0、控制栏消失，或此前修复的闪现 / 误锁再次出现，提供版本、简单复现步骤和诊断即可。body 空档、pagehide 后的停止与恢复及控件移除竞态由合成回归覆盖，不需要人为破坏实际聊天文档。

## 内存验证

折叠不删除原 DOM，也不卸载站点 JavaScript 状态。**页面变短、滚动更顺滑、DOM 节点减少、JavaScript 堆下降、进程内存下降是不同现象，应分别记录。**

0.1.6 的维护诊断也不是内存测量仪。记录数等于当前已挂载回答、队列清空和未持有断开记录，可以验证特定清理条件；这些数字既不是 MB，也不能证明站点数据或浏览器缓存受到相同上限约束。合成基准见 [MEMORY.md](MEMORY.md)，真实标签页对照按以下方法另外记录。

### 对照条件

选择一段你经常卡顿的实际长对话。记录 Chrome 版本、操作系统、对话大致轮数、富内容类型和扩展版本。

尽量保持以下条件一致：

- 同一段对话、窗口大小、页面缩放和页面位置。
- 不在生成回答时测量，等待网络、图片和字体加载稳定。
- 关闭其他影响页面的扩展或保持两组设置相同。
- 测试过程中不要新增大量消息、切换模型或同时运行不同负载。
- 为每次冷加载提供相近的等待时间，至少重复 3 组对照，报告范围或中位数。

### 建议步骤

1. **基线 A：** 关闭 ChatGPT Fold 效果，重新加载同一段对话，等待稳定并记录。
2. **折叠 B：** 开启扩展，设置最近 1 条 / 上限 1，重新加载同一段对话，用相同条件记录。
3. **往返操作：** 在 B 中交替打开不同历史回答，完成约 20 次展开 / 收起，再记录。
4. **恢复检查：** 在可稳定运行的内容规模下临时恢复正文，验证内容正确；继续折叠，再记录一次。对已经接近卡死的长对话，先逐条展开检查，不以全部展开作为必要测量步骤。
5. **清理检查：** 连续切换若干对话，检查计数是否回到当前页范围，以及是否出现持续增长趋势。

应使用分别重新加载的 A/B 结果进行主要比较；同一次页面加载中反复切换只能作为补充，因为先前分配的内存可能被浏览器缓存。

### 记录哪些指标

| 指标 | 在哪里看 | 如何理解 |
| --- | --- | --- |
| 标签页相关内存 | Chrome 任务管理器，通常可用 `Shift+Esc` 打开 | 更接近使用者实际压力，但可能包括缓存和共享进程影响 |
| JavaScript 内存 | 任务管理器的 JavaScript 内存列或 DevTools | 折叠不会主动删除站点 JS 状态，不保证下降 |
| DOM 节点数 | DevTools Performance monitor 等工具 | 原节点保留；少量新增扩展控件属预期 |
| 扩展记录与待处理队列 | 弹窗诊断的登记数与 `maintenance` | 检查扩展清理与队列状态，不能换算为总内存 |
| 布局 / 绘制与 CPU | DevTools Performance / Performance monitor | 检查同类滚动或展开操作的渲染代价 |
| 响应与错误 | 实际滚动、点击、生成和控制台 | 节省资源的同时必须保证内容可用 |

Chrome 版本和平台可能改变工具菜单或列名。参考 [Chrome DevTools 内存问题指南](https://developer.chrome.com/docs/devtools/memory-problems)。

### 比较时的注意点

- DevTools 自身会改变页面性能；两组应使用相同的工具状态。可先用任务管理器做低干扰对照，再用 DevTools 诊断原因。
- 页面当前还持有的对象不会因为触发垃圾回收而自动释放；强制回收只适合诊断，且两组条件要相同。
- 浏览器释放了对象后，也未必立即把相同大小的内存返还给操作系统。
- 不要把 DOM 节点计数当成内存大小，也不要仅根据 JS 堆推算整个标签页占用。
- 有意保留的活动页面节点与“离开对话后仍被扩展引用的节点”应分开判断。用堆快照排查时，不要因看到一个 detached 节点就直接认定是扩展泄漏。
